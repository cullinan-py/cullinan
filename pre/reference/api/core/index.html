    The core namespace¶

    cullinan.core holds the container, the lifecycle, the request context and the object model.

    cullinan.core ¶

    Core module for Cullinan framework.

    This module provides foundational components for the Cullinan framework: - ApplicationContext: Single entry point for IoC/DI - Decorators: @service, @controller, @component - Dependency Injection: Inject, InjectByName, Lazy - Unified lifecycle management (all components share same lifecycle) - Core exceptions and types

    The runtime version comes from cullinan/_version.py (single source of truth).

    Registry ¶

    Registry()

    Bases: ABC, Generic[T]

    Abstract base class for all registries in Cullinan.

    Provides common functionality for registration, retrieval, and management of framework components with performance optimizations.

    Performance features: - Fast O(1) lookups using dict - Lazy metadata initialization (only created when needed) - Batch registration support - Hook system for pre/post registration callbacks - Thread-safe operations (when using proper locking in subclasses)

    Name Bound or Constraints Description Default

    The type of items this registry manages

    		 required
    Usage

    Initialize an empty registry with optimized storage.

    SmartLifecycle ¶

    Bases: LifecycleAware

    Extended lifecycle with phase control.

    Allows controlling startup/shutdown order through phase numbers. Lower phase = starts earlier, stops later.

    get_phase ¶

    get_phase()

    Return the phase value for this component.

    Default is 0. Lower values start earlier and stop later.

    Examples: - Database: -100 (starts very early) - Cache: -50 - Business services: 0 (default) - Web controllers: 50 (starts late)

    RequestContext ¶

    RequestContext()

    Container for request-scoped data.

    This class holds data that is specific to a single request, such as user information, request metadata, and temporary state.

    Features can be controlled via configuration (v0.81+): - auto_request_id: Automatic request ID generation - timing: Request timing tracking - metadata: Metadata storage support - cleanup_callbacks: Cleanup callback support - debug_logging: Debug-level logging

    Example

    In a handler¶

    ctx = RequestContext() ctx.set('user_id', 123) ctx.set('request_id', 'abc-123')

    Later in the same request¶

    user_id = ctx.get('user_id')

    Initialize a new request context.

    ScopeViolationError ¶

    ScopeViolationError(message, dependency_chain=None, origin_name=None, violating_component=None, **kwargs)

    Bases: LifecycleError

    Whether new request scopes are still accepted.

    shutdown ¶

    shutdown(timeout=30.0)

    Shut the container down, waiting for in-flight request scopes.

    Returns True when the drain completed within timeout, and False when the deadline passed -- or when the wait was skipped because a running event loop made a blocking wait unsafe. A caller can therefore tell a clean drain from a timed-out one without reading logs.

    ashutdown async ¶

    ashutdown(timeout=30.0)

    Async counterpart of :meth:shutdown for callers already on a loop.

    shutdown() waits for in-flight request scopes with a blocking sleep. Called from inside a running event loop -- which is exactly what the ASGI lifespan shutdown handler does -- that sleep starves the very tasks the drain is waiting for: the scope count never falls, the wait burns the whole timeout and the in-flight requests are dropped. This coroutine yields control back to the loop while it waits, so the drain can actually complete.

    The close itself runs on the same single timeout source (WebRuntimeConfig.drain_timeout) as the synchronous path.

    await_drained async ¶

    await_drained(timeout=30.0)

    Wait until no request scope is active, without blocking the loop.

    Returns True when the container drained within timeout and False when the deadline passed with scopes still active. Unlike the internal blocking wait used by :meth:shutdown, this never blocks the event loop, so the in-flight tasks can run to completion.

    add_draining_handler ¶

    add_draining_handler(handler)

    Register a callback fired when the container starts draining.

    The Python-native counterpart of a "readiness turned off" signal: a plain callable (sync or async) invoked once, on the transition into draining, before in-flight requests are awaited. Subscribers typically flip a flag their own probe or load balancer consults, so the framework supplies the mechanism and never dictates a route or a port.
