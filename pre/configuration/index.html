    Configuration¶

    Cullinan reads project settings from one configuration file, not from a .env file and not from a dozen scattered environment variables.

    {
  "server_port": 8080,
  "server_host": "0.0.0.0",
  "server_engine": "asgi"
}

    application.run(main) reads it. There is nothing to import and nothing to call.

    Why a file and not .env¶

    .env is a flat KEY=VALUE list. It has no nesting, no types, and no way to say "this value comes from somewhere else". It also cannot answer the question a packaged build actually has: where does this file live, and did it end up inside the artefact that was shipped?

    A configuration file answers all four, which is why python-dotenv — previously the framework's only runtime dependency — is no longer used. Cullinan now has no runtime dependencies; JSON is read with the standard library.

    File names¶

    File When it is read
    application.json always, when present
    application-<profile>.json merged over the base when CULLINAN_PROFILE is set

    .toml, .yaml and .yml are read too, but only when the interpreter or the environment can parse them — TOML needs Python 3.11+ (or tomli), YAML needs pyyaml. When the parser is missing, the error names the package to install instead of silently loading nothing. JSON needs nothing, so it is the format that always works.

    Where the file is looked for¶

    In order:

    1. the path given by CULLINAN_CONFIG, or passed as load_project_config(path=...)
    2. the working directory
    3. the directory of the executable that was launched

    The installed package is never searched

    A configuration file inside the installed package would be a bug in two directions: it would ship your settings inside the artefact, and a stale copy inside the bundle would shadow the file you edited next to the binary. Only the two locations above are searched, and a test holds that.

    An explicit path that does not exist is an error. Falling back to defaults after someone named a file would hide a typo until production.

    Precedence¶

    Highest first:

    # Source Example
    1 argument to run() run(main, port=9090)
    2 environment variable SERVER_PORT=9090
    3 configure(...) @configure(server_port=9090)
    4 configuration file {"server_port": 9090}
    5 built-in default 4080

    A value written in code wins over the file because the file is applied first; an environment variable wins over both because it is read when the value is used.

    Keep secrets out of the file¶

    A file that is committed, or shipped beside a binary, is not a place for a secret. Two features exist so it does not have to be:

    {
  "discord": {
    "token": "${DISCORD_TOKEN}",
    "fallback_channel": "${DEFAULT_CHANNEL:general}"
  }
}
    • ${VAR} is replaced by the environment variable, after the file is read.
    • ${VAR:default} falls back to default when the variable is not set.
    • A placeholder with neither a value nor a default raises. Substituting an empty string would turn a missing setting into one that looks configured — the failure would surface later, somewhere less obvious.

    If the file must carry ciphertext¶

    Pass a decryptor. Cullinan does not ship one:

    from cullinan.support.config_file import load_project_config

config = load_project_config(decryptor=my_decrypt)   # {"encrypted": "..."} → plain

    A key that sits beside the ciphertext is not encryption, so the framework does not pretend otherwise. The key belongs to the deployment — an environment variable, a secret manager, an HSM — and stays outside the artefact.

    Packaging¶

    Compiling the application raises the cost of reading your code; it does not make shipped data secret. A configuration file placed inside a bundle can be extracted from that bundle. So the guidance is positional, not cryptographic:

    • Do not bundle the configuration file. Put it next to the executable, or point CULLINAN_CONFIG at it. Cullinan never looks inside the package, so a bundler configuration that copies it in gains nothing.
    • Let the file hold references, not values. ${VAR} keeps the secret in the environment where the secret manager put it.
    • Decide per setting whether it must be secret at all. A port number is not a secret; a bot token is. Splitting the file along that line is more effective than encrypting all of it.

    For how a packaged application resolves its own directories, see Packaging — the same distinction between "where the code is" and "where the user's data is" applies here.

    Complete example¶

    {
  "server_port": 8080,
  "server_host": "0.0.0.0",
  "server_engine": "tornado",
  "verbose": true,
  "discord": {
    "token": "${DISCORD_TOKEN}"
  }
}

    from cullinan import application, configure


@configure(user_packages=["myapp"])
@application
def main():
    ...


if __name__ == "__main__":
    main()

    CULLINAN_PROFILE=prod DISCORD_TOKEN=... python -m myapp

    application-prod.json in the same directory is merged over application.json before the values are used.

    A runnable version lives in examples/config_file.

    Migrating from .env¶

    Every key in .env has a home in the file, and nested keys are easier to read:

    .env application.json
    SERVER_PORT=8080 {"server_port": 8080}
    DISCORD_TOKEN=abc {"discord": {"token": "${DISCORD_TOKEN}"}}
    — profile switching via CULLINAN_PROFILE

    Reading .env is no longer supported, and the dependency that provided it has been removed. If your deployment already exports those variables, nothing needs to change: environment variables still take precedence over the file.

    Reading the configuration in code¶

    from cullinan.support import get_config

port = get_config().server_port

    If you want the raw document rather than framework settings:

    from cullinan.support.config_file import load_project_config

settings = load_project_config()          # {} when there is no file

    load_project_config() never raises for a missing file — an application without a configuration file is a valid application. It does raise for a file it cannot parse, a placeholder it cannot resolve, and an explicit path that does not exist.
