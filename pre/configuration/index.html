    Configuration¶

    Cullinan reads project settings from one configuration file, not from a .env file and not from a dozen scattered environment variables.

    {
  "server_port": 8080,
  "server_host": "0.0.0.0",
  "server_engine": "asgi"
}

    application.run(main) reads it. There is nothing to import and nothing to call.

    Why a file and not .env¶

    .env is a flat KEY=VALUE list. It has no nesting, no types, and no way to say "this value comes from somewhere else". It also cannot answer the question a packaged build actually has: where does this file live, and did it end up inside the artefact that was shipped?

    A configuration file answers all four, which is why python-dotenv — previously the framework's only runtime dependency — is no longer used. Cullinan now has no runtime dependencies; JSON is read with the standard library.

    File names¶

    File When it is read
    application.json always, when present
    application-<profile>.json merged over the base when CULLINAN_PROFILE is set

    .toml, .yaml and .yml are read too, but only when the interpreter or the environment can parse them — TOML needs Python 3.11+ (or tomli), YAML needs pyyaml. When the parser is missing, the error names the package to install instead of silently loading nothing. JSON needs nothing, so it is the format that always works.

    Which keys a file may contain¶

    The accepted set is the field names of CullinanConfig, and the framework derives it from that class instead of listing it a second time -- a list here would be a second truth, and it would drift the first time someone added a field in a hurry. There are 32, in five groups:

    Group Keys
    discovery user_packages, project_root, exclude_packages, auto_scan, explicit_modules
    server server_engine, asgi_server, server_host, server_port, drain_timeout, max_request_body_bytes, ssl_certfile, ssl_keyfile, ssl_client_ca, ssl_verify_client
    routing route_trailing_slash, route_case_sensitive, enable_middleware_pipeline
    OpenAPI openapi_enabled, openapi_title, openapi_version, openapi_description
    runtime / assembly verbose, debug, startup_error_policy, static_files, middlewares, builtin_middleware, context_features, strict_assembly, strict_assembly_excludes

    root_module is a 28th field kept so existing decorators keep importing; passing it at start-up is an error, not a setting.

    A key outside this set is reported when the file is loaded -- naming the key, the file it came from and, when the spelling is close, the name that was probably meant -- and it is not applied. A key cannot be accepted and ignored: a typo and a working switch used to look identical, and the difference only showed up in the behaviour the switch was supposed to change. openapi_enabled: false was one of nine keys in that state.

    A boolean may be written as true/false (JSON, TOML, YAML), or as 1/0, yes/no, on/off in quotes. Anything else is refused with the key named, because bool("false") is True -- guessing is how a switch becomes silent again.

    max_request_body_bytes is described in deployment: what a client observes when an upload crosses the ceiling depends on the engine and on whether the client is still writing when the server refuses, and one of those outcomes carries no status code at all.

    The refusal itself happens before the body is accepted, on both engines. A request whose Content-Length already exceeds the ceiling is answered 413 without reading it — a client that sends slowly, or never finishes, still gets its answer at once. A chunked upload declares no size, so it is stopped when the bytes received cross the ceiling. Tornado refuses at max_body_size before the framework sees the request at all; what the client can read of that refusal is the part that depends on timing.

    Where the file is looked for¶

    In order:

    1. the path given by CULLINAN_CONFIG, or passed as load_project_config(path=...)
    2. the working directory
    3. the directory of the executable that was launched

    The installed package is never searched

    A configuration file inside the installed package would be a bug in two directions: it would ship your settings inside the artefact, and a stale copy inside the bundle would shadow the file you edited next to the binary. Only the two locations above are searched, and a test holds that.

    An explicit path that does not exist is an error. Falling back to defaults after someone named a file would hide a typo until production.

    Precedence¶

    Highest first:

    # Source Example
    1 argument to run() run(main, port=9090)
    2 environment variable SERVER_PORT=9090
    3 configuration file {"server_port": 9090}
    4 configure(...) @configure(server_port=9090)
    5 built-in default 4080

    The file sits above the values declared in code because it is applied after them: one binary, several deployments, and the deployment answers for its own addresses. That order is what makes "roll back by editing one file" possible, and an earlier revision of this page described the opposite one -- the table now matches what the code does, and a test holds it (configure(server_port=A) plus a file saying B must serve on B; with no file it must serve on A), so the page cannot drift back to the order it used to describe.

    run(...) overrides the file for the two names it accepts, and an environment variable is read at use time, so it wins over both. Every other name has one decider: the file if it is there, otherwise the value written in code, otherwise the default.

    The environment variables this framework reads are a short list — CULLINAN_CONFIG, CULLINAN_PROFILE, CULLINAN_ENGINE, SERVER_HOST, SERVER_PORT — and the engine is not the one a reader expects: it is chosen with CULLINAN_ENGINE. SERVER_ENGINE is not a variable this framework reads. SERVER_HOST and SERVER_PORT are, which is what makes the mistake natural: a deployment that sets SERVER_ENGINE=tornado gets whatever auto picks, with no error at all — so two runs that were meant to compare engines can both be the same engine, and the difference observed between them is then imagined.

    Start-up prints the engine and the layer that chose it, so the question is answered by the log rather than by reading the source:

    └---Web engine: tornado (decided by: environment (CULLINAN_ENGINE))

    The other three forms it can take are run(engine='tornado'), configuration file (server_engine) and built-in default (auto).

    Options in code¶

    @configure(...) takes its own set of options — the parameters of configure() — and that is not the same list as the keys a file may contain. Two consequences follow:

    • an option configure() does not have is refused, with a TypeError that names it, offers the closest name it does accept, and points at this section. Accepting a misspelling with a warning was considered and rejected: the switch would look set and change nothing, which is the failure this page keeps coming back to. The exception type is still TypeError, so a caller that already catches it keeps working;
    • when a setting is named in both places, the file wins — see Precedence. That is what makes "roll back by editing one file" true, and it is why the rollback unit across the 0.96 line is a pin and a configuration, not the pin alone (migration guide).

    To see the exact list for the installed version, ask it:

    import inspect

from cullinan import configure

print(sorted(inspect.signature(configure).parameters))

    That is the same source the error message reads, so the message and the list cannot drift apart. The supported way to ask the same question — and the one that also makes a single call work against two installed versions — is configure_options(), shown in the migration guide.

    Keep secrets out of the file¶

    A file that is committed, or shipped beside a binary, is not a place for a secret. Do not write a value into the file. What belongs there is safe to paste into an issue tracker, because sooner or later it ends up in one.

    The file is ignored by default. application*.json, application*.toml, application*.yaml and application*.yml are in .gitignore, so a plain git add . does not commit a file that carries a value. The template form — application*.example.json and the .toml / .yaml / .yml equivalents — stays trackable: that is the shape meant to be committed, and it holds references instead of values. An ignore rule is a default rather than a wall (git add -f walks past it), so a repository check reads every application* file twice — the copy on disk and the copy in the index — and reports a plaintext value in either one. They are not the same copy and either can carry a value: the index copy is what a push would send, and an edit on disk that has not been staged is the next thing that will be. It reports a value under a sensitive key, or a value whose shape is a known credential form (a PEM private-key header, an AWS access-key id, a GitHub token), whatever the key is called.

    JSON and TOML are read as documents where the interpreter can parse them — TOML needs Python 3.11+. Otherwise the file is read line by line and the fallback is reported, never silent, which is also how a YAML file is always read: a value written as a multi-line block is reported as undecided rather than quietly passed.

    Two consequences worth knowing:

    • Naming a file through CULLINAN_CONFIG puts it outside every rule here — the name can be anything. Keep that file out of version control yourself.
    • A file that is already committed stays committed. The rule stops the next git add .; it does not rewrite history. Deleting the file is not the same as removing it: until the deletion is committed — and, for a value that was pushed, until history is rewritten — the copy is still there to be fetched. The check itself reads the working tree and the index; it does not read HEAD, so a value that was committed and later removed from the index is out of scope here.

    Do not print it either. get_config() hands back resolved values, so a print or a debug log of the whole document writes the secret into a terminal, a log file or a CI transcript — a second copy, with none of the protections the first one had. Print the setting you mean, not the document.

    The alternative is to write a reference where a value would go, which two features support:

    {
  "discord": {
    "token": "${DISCORD_TOKEN}",
    "fallback_channel": "${DEFAULT_CHANNEL:general}"
  }
}
    • ${VAR} is replaced by the environment variable, after the file is read.
    • ${VAR:default} falls back to default when the variable is not set.
    • A placeholder with neither a value nor a default raises. Substituting an empty string would turn a missing setting into one that looks configured — the failure would surface later, somewhere less obvious.

    If the file must carry ciphertext¶

    Pass a decryptor. Cullinan does not ship one:

    from cullinan.support.config_file import load_project_config

config = load_project_config(decryptor=my_decrypt)   # {"encrypted": "..."} → plain

    A key that sits beside the ciphertext is not encryption, so the framework does not pretend otherwise. The key belongs to the deployment — an environment variable, a secret manager, an HSM — and stays outside the artefact.

    Packaging¶

    Compiling the application raises the cost of reading your code; it does not make shipped data secret. A configuration file placed inside a bundle can be extracted from that bundle. So the guidance is positional, not cryptographic:

    • Do not bundle the configuration file. Put it next to the executable, or point CULLINAN_CONFIG at it. Cullinan never looks inside the package, so a bundler configuration that copies it in gains nothing.
    • Let the file hold references, not values. ${VAR} keeps the secret in the environment where the secret manager put it.
    • Decide per setting whether it must be secret at all. A port number is not a secret; a bot token is. Splitting the file along that line is more effective than encrypting all of it.

    For how a packaged application resolves its own directories, see Packaging — the same distinction between "where the code is" and "where the user's data is" applies here.

    Complete example¶

    {
  "server_port": 8080,
  "server_host": "0.0.0.0",
  "server_engine": "tornado",
  "verbose": true,
  "discord": {
    "token": "${DISCORD_TOKEN}"
  }
}

    from cullinan import application, configure


@configure(user_packages=["myapp"])
@application
def main():
    ...


if __name__ == "__main__":
    main()

    CULLINAN_PROFILE=prod DISCORD_TOKEN=... python -m myapp

    application-prod.json in the same directory is merged over application.json before the values are used.

    A runnable version lives in examples/config_file.

    Migrating from .env¶

    Every key in .env has a home in the file, and nested keys are easier to read:

    .env application.json
    SERVER_PORT=8080 {"server_port": 8080}
    DISCORD_TOKEN=abc {"discord": {"token": "${DISCORD_TOKEN}"}}
    — profile switching via CULLINAN_PROFILE

    Reading .env is no longer supported, and the dependency that provided it has been removed. If your deployment already exports those variables, nothing needs to change: environment variables still take precedence over the file.

    Reading the configuration in code¶

    from cullinan.support import get_config

port = get_config().server_port

    If you want the raw document rather than framework settings:

    from cullinan.support.config_file import load_project_config

settings = load_project_config()          # {} when there is no file

    load_project_config() never raises for a missing file — an application without a configuration file is a valid application. It does raise for a file it cannot parse, a placeholder it cannot resolve, and an explicit path that does not exist.
